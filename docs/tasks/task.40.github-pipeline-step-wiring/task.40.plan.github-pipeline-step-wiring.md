# Implementation Plan: wire `gh-stage.js` into the step files

> Requirements and success criteria: [task.40.github-pipeline-step-wiring.md](task.40.github-pipeline-step-wiring.md)

## Overview

Replace five inline `gh api graphql` blocks with one-line CLI calls, in rising blast-radius order.
All edits go in `shared/resources/` (and `skills/finalise/SKILL.md`, which is skill-native); the
`skills/*/references/` copies are regenerated by `npm run bundle` in the same commit.

## Phase-by-Phase Implementation Guide

### The replacement shape

Every site collapses to this, matching the adjacent `jira-stage.js` calls so a reader sees one
pattern for both trackers:

```bash
node .agents/skills/{develop-story|develop-task|develop-bug}/references/gh-stage.js \
  --issue {TRACKER_ISSUE} --stage <moment> --json
```

`{develop-story|develop-task|develop-bug}` brace form is what the shared step files already use for
`jira-stage.js`; `tests/executable-instructions.test.js` already tolerates it.

### Phase 1: Step 4 — `develop-pipeline-step-4-create-pr.md`

Delete L178-238. Three things go with it:

1. **L182** — `BOARD_NUM=$(grep 'project_board_number:' project.yml | awk '{print $2}')`, computed
   and never used. Dead since it was written.
2. **L211-212** — the field/option `jq` selectors.
3. **L237** — the paragraph that is the clearest statement of the problem being fixed:

   > "The board must have a Status column option named exactly **"In Review"**. If the project uses
   > a different label (e.g. "Review", "Code Review"), the option lookup returns empty and the block
   > logs a skip — update `select(.name == "In Review")` to match the exact option name."

   Replace with:

   > The column this lands in comes from `pipeline.in-review` in `tracker-workflow.yaml`. Run
   > `gh-stage.js --probe-board` to see your board's real options and which moment each resolves to.

Decisions Log line becomes: `"GitHub board: in-review → {landed / already / no-option / would-regress}."`

### Phase 2: Step 5-6 — `develop-pipeline-step-5-6-qa-loop.md`

Replace L43-106. Two deliberate changes beyond the mechanical swap:

**No `--allow-regress`.** Today the block force-writes "In Review" over whatever the card is on
(L77 short-circuits only when it is *already* In Review). With the guard, a card a human advanced to
a higher rung correctly refuses. Add prose:

> This re-assert is guarded. A card someone has already advanced past review — to a showcase or
> merge column — will log `would-regress` and stay where it is. That is correct: the board is ahead
> of the pipeline, not behind it.

**Drop the hand-rolled already-check** at L77 (`if [ "$CURRENT_STATUS" ... ] = "in review"`). The CLI
returns `reason: "already"` and makes no mutation.

Keep the "run once, before the first cycle, not per cycle" rule verbatim — it is unchanged and
correct.

### Phase 3: Step 0 — `develop-pipeline-step-0-resolve-and-prepare.md`

The largest and most entangled block (L364-504). It carries **three** concerns; separate carefully.

**Concern 1 — board membership.** L376-378 plus the retry-on-empty at L410-444:

```bash
gh project item-add "$BOARD_NUM" --owner "$OWNER" --url "$REPO_URL/issues/{TRACKER_ISSUE}"
sleep 3                      # Projects API propagation
# ... if projectItems empty: sleep 5, re-query once
```

This is real Projects-API propagation behaviour, not step-file scaffolding. It moves **into**
`gh-stage.js`'s `ensureOnBoard` (task.39) and is invoked with `--add-to-board`. Port it verbatim;
do not re-derive the sleep values.

**Concern 2 — Status.** Replaced by the CLI call.

**Concern 3 — Priority → P2 when unset** (L473-486). A different concern that merely shares the
GraphQL response. Two acceptable outcomes:

- *Preferred*: delegate to `shared/resources/set-github-project-priority.sh`, which already derives
  priority from labels; it needs a skip-if-already-set path added.
- *Acceptable*: leave the priority block inline and strip only the Status half out of it. Take this
  if delegating proves invasive — this task is already the riskiest in the series.

**Delete the post-condition block** (L493-500):

```bash
if [ "$BOARD_STATUS" = "Todo" ] || [ "$BOARD_STATUS" = "unknown" ]; then
  echo "⚠️  POST-CONDITION FAILED: ..."
else
  echo "✅ Post-condition verified: board status is '$BOARD_STATUS'"
fi
```

This is not merely redundant — it is **wrong**. It asks "is the card still in the literal column
`Todo`?", so a board whose first column is `Backlog` prints "✅ Post-condition verified" after a
move that failed. `gh-stage.js` re-reads and reports the landed option, which is the check this was
trying to be.

Report table row: `| Board status | {landed option} ✅ / ⚠️ {reason} |`.

### Phase 4: Step 7 and `/finalise`

**`develop-pipeline-step-7-finalise.md:165`** — currently prose delegating to another file's
pattern:

> "move the project board item to Done using the same GraphQL pattern from
> `develop-pipeline-step-0-resolve-and-prepare.md` (0c-reg GitHub path), but with
> `ascii_downcase == "done"` as the target option match (not "in progress")"

Replace with an explicit call. Note in the step file that `stage-disabled` — a consumer who omitted
`done:` from `pipeline:` because a human moves the final card — is a **success**, not a warning.

**`skills/finalise/SKILL.md:1023-1093`** — the same call. This fixes the case-sensitivity bug by
construction: L1061 currently reads

> The option in that field where `name == "Done"` → its `id` is the singleSelectOptionId

while every step file uses `ascii_downcase`. One engine, one rule.

**Keep the escalation.** L1063-1073 posts a PR comment when the issue is on no board. `gh-stage.js`
returns `reason: "not-on-board"`; branch on it. `/finalise` is the one caller that treats a board
miss as noteworthy — the pipeline steps shrug at it — and that decision belongs in the skill, not
buried in the CLI.

**Reorder `/finalise`.** It currently drives Done first via a `sync-jira-{story,task}.js` re-run
(L916-927), which resolves through `loadStatusMap` — a *different* config source from the ladder. So
one skill resolves Done two ways from two places. Fix by ordering, not a new flag: run the stage
call **first**, then the sync re-link. The sync's own transition then resolves to `already` and
no-ops, the re-link keeps doing its real job (re-pointing the Document link at the durable branch),
and the workflow file becomes the single resolver.

**`develop-pipeline-lite-mode.md:32`** — prose only; name the CLI instead of the GraphQL verb.

### Phase 5: Guards, bundle, docs

**Grep guard**, in `evals/shared/tests/transition-protocol-parity.test.mjs`:

```js
// Absence alone is a bad guard — v0.33 records one that flagged the very sentence
// that got it right. So pair it: no inline board mutation ANYWHERE, and each step
// positively invokes the CLI.
for (const f of shippedMarkdown()) {
  const src = readFileSync(f, "utf-8");
  if (src.includes("updateProjectV2ItemFieldValue"))
    assert.ok(!/"Status"/.test(src), `${f} still carries an inline board Status mutation`);
}
assert.match(step4, /gh-stage\.js[\s\S]{0,120}--stage in-review/);
assert.match(step56, /gh-stage\.js[\s\S]{0,120}--stage in-review/);
assert.match(step0, /gh-stage\.js[\s\S]{0,120}--stage work-started/);
assert.match(step7, /gh-stage\.js[\s\S]{0,120}--stage done/);
```

Exempt `set-github-project-priority.sh` / `set-github-project-estimate.sh` — they legitimately
mutate other fields.

Extend the existing `--stage` literal scan (that file, L72-97) to the `gh-stage.js` call sites; it
matches the literal rather than the script name, so it may already cover them — verify.

**Bundle**: `npm run bundle`, then commit the regenerated `skills/*/references/`. Add to
`.github/workflows/validate.yml`:

```yaml
- run: npm run bundle && git diff --exit-code -- 'skills/*/references/*'
```

Today CI checks the catalog only, and `scripts/release.sh:184` catches bundle drift after review.

**CHANGELOG** — one entry per user-visible consequence:

- *Changed*: step files no longer carry inline GraphQL; where the option-name literals went and why.
- *Changed*: GitHub board moves are guarded against regression; what `would-regress` means.
- *Fixed*: `/finalise` matched `"Done"` case-sensitively while every step file did not.
- *Fixed*: the step-0 post-condition compared against the literal column `Todo`, so any board whose
  first column was named otherwise reported success after a failed move.

## Key Patterns and References

- `jira-stage.js` invocations in the same files — `step-0:336-345`, `step-4:257-263`,
  `step-5-6:28-38` and `:250-258`, `step-7:205-213`. Match their shape, their `--json` handling and
  their Decisions Log wording.
- `AGENTS.md` — bundling rules. `shared/resources/` is the only editable source.
- `tests/executable-instructions.test.js` — validates that every referenced script path exists in
  the bundles.
- `evals/develop-{story,task}/protocol/` — step-contract keyword expectations that will need
  updating in the same commit.

## Testing Approach

- After each phase: `npm run bundle && npm test`. Do not batch four phases and then test.
- `--dry-run` at each rewritten site against a real issue before any real run.
- One full `/develop-task` run against a scratch Projects v2 board with deliberately bespoke column
  names (`Backlog / In Development / Ready for Showcase / Shipped`) — the end-to-end proof that a
  consumer's ladder drives the board.
- Explicitly verify the guard: manually advance a card to a higher rung, then re-enter the QA loop
  and confirm it logs `would-regress` and stays put.
