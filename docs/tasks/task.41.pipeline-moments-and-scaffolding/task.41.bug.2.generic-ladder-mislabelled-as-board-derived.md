# Bug Report: Task 41 — a generic Jira ladder is reported as "generated from your live board"

**Task**: [task.41.pipeline-moments-and-scaffolding.md](./task.41.pipeline-moments-and-scaffolding.md)
**Bug ID**: TASK-41-BUG-2
**Severity**: MEDIUM
**Priority**: P2
**Status**: ✅ Ready for QA
**Found By**: QA Engineer
**Date Found**: 2026-08-12

## Description

`jira-stage.js --init-workflow` always writes a file and always exits 0. When no `jira.workflowRecord` exists it writes a **generic** three-rung ladder and emits a deliberately loud warning:

> ⚠️  No workflow record to convert — this is a GENERIC ladder and your board's real columns are almost certainly different. A ladder that does not match resolves nothing, and fails SILENTLY.

`write_tracker_workflow()` invokes it as `node "$_cli" --init-workflow >/dev/null 2>&1`, which **discards that warning**, then reports `generated from your live board` and records `generated from board`.

The consumer is told their file came from their board when it is a template, and the one message telling them to edit it is suppressed.

## Steps to Reproduce

```bash
mkdir /tmp/jira-consumer && cd /tmp/jira-consumer && git init -q .
# no docs/development/jira-workflow.json present
node .agents/skills/develop-task/references/jira-stage.js --init-workflow >/dev/null 2>&1; echo "exit=$?"
head -2 tracker-workflow.yaml
```

Observed: `exit=0`, file header `# Generated by \`jira-stage --init-workflow\`.` — no record, generic ladder, warning swallowed.

## Expected Behavior

Either the wizard distinguishes a record-derived file from a generic one and labels it accordingly (with the "edit before first run" warning surfaced), or it does not claim board provenance it cannot verify.

## Actual Behavior

Both outcomes are reported identically as `generated from board`, and the CLI's own warning is redirected to `/dev/null`.

## Impact

A generic ladder that does not match the board **resolves nothing and fails silently** — the pipelines run, report success, and move no cards. That is precisely the failure mode the loud warning exists to prevent, and precisely the one the wizard's redirect removes. The consumer also loses the `record_warning` line that would otherwise appear in the wizard's closing summary.

Lower severity than BUG-1 only because a usable file *does* land on disk.

## Recommendation

`initWorkflow()` already returns `fromRecord: true|false` in its JSON payload. Use it:

```bash
_out=$(node "$_cli" --init-workflow --json 2>/dev/null)
if [[ -f "tracker-workflow.yaml" ]]; then
  if [[ "$(printf '%s' "$_out" | jq -r '.fromRecord // false' 2>/dev/null)" == "true" ]]; then
    record_step "tracker-workflow" "ok" "generated from board"
  else
    warn "Wrote a GENERIC ladder — edit it to match your board before the first run."
    record_warning "tracker-workflow.yaml is generic — edit it before the first pipeline run"
    record_step "tracker-workflow" "ok" "template (edit before first run)"
  fi
  return
fi
```

This also fixes BUG-1's exit-code inference in the same block.

## Developer Fix Cycle

### Iteration 1

#### Investigation (New → In Progress)

**Date**: 2026-08-12

**Root Cause**: Two outcomes — a record-derived file and the CLI's own generic
fallback — were reported identically, and `>/dev/null 2>&1` discarded the CLI's
loud warning about the second. The information needed to tell them apart already
existed: `initWorkflow()` returns `fromRecord` in its `--json` payload.

#### Fix Implementation (In Progress → Ready for QA)

**Date**: 2026-08-12

**Fix Description**: The probe now runs with `--json`, captures stdout, and
branches on `.fromRecord`. True → "generated from your live board". False → the
file is kept but reported as `template (edit before first run)`, with the
three-line generic-ladder warning re-emitted by the wizard itself and a
`record_warning` added so it also appears in the closing summary.

**Files Modified**:
- `scripts/setup-consumer.sh`
- `shared/resources/tests/setup-consumer-config.test.mjs` — stub tests for both labels

**Testing**: Verified against the real `jira-stage.js` with no workflow record —
now reports the template label and surfaces all three warning lines. Pinned by
"probe branch: a CLI that writes a GENERIC file is labelled as a template,
loudly".

**Verification Steps for QA**:
1. Jira consumer with no `docs/development/jira-workflow.json`; run the writer.
2. Confirm the output says `template (edit before first run)`, not board-derived,
   and that the GENERIC-ladder warning is visible.
