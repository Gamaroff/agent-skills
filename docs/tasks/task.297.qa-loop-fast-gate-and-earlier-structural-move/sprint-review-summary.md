## Summary

The QA loop now records when it has no fast gate to run, instead of skipping in silence. Its rule for "the same finding came back" is now a small script, so the offer to restructure fires at the second repeat.

---

## What Was Delivered

### Acceptance Criteria Met

- [x] An unset `develop.fastGateCommand` records `Fast gate: skipped (develop.fastGateCommand unset)`. It is still a skip, not a halt.
- [x] Two consecutive gates naming one file that the previous fix edited trigger the offer. A different file, or a shared file the fix did not edit, does not.
- [x] The diagnosis of why task.295's loop never ran the full suite after a fix is recorded in the task document.
- [x] A repository with the key set sees no extra gate runs.
- [x] `bundle:check` and `ci:fast` pass.
- [x] Each fix is mutation-proved: the test goes red when the behaviour is reverted.
- [x] `CHANGELOG.md` states the unset-key behaviour.

### Key Features Implemented

- **Fast-gate presence check**: `fast-gate-outcome.sh --command` answers `skipped` or `run`, and step 0a of the QA loop records the skip.
- **Repeat-subject rule**: `repeat-subject.mjs` decides whether a finding is a repeat; `qa-fix` trigger (b) calls it.

## Known Limitations & Future Work

- A command made only of Unicode blanks (for example U+00A0) reads as `run`. The task's "empty or whitespace" wording does not say which whitespace counts.
- `repeat-subject.mjs --fix-commit` does not reject a value starting with `-`. The caller is the pipeline, so impact is low.
- Two LOW cleanups from the QA gate: single-quote the substituted command in step 0a, and scope trigger (b)'s previous-fix lookup to `fix(task.{id})`.
