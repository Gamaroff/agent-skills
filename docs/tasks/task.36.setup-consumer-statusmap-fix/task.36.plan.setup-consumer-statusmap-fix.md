# Implementation Plan: Stop `setup-consumer.sh` generating a narrowing `jira.statusMap`

> Requirements and success criteria: [task.36.setup-consumer-statusmap-fix.md](task.36.setup-consumer-statusmap-fix.md)

## Overview

Delete the live `statusMap:` YAML from the wizard's Jira config block, fix the documentation that
mirrors it, and add a read-only detector so consumers already carrying the block can find out.

## Phase-by-Phase Implementation Guide

### Phase 1: Remove the generated block

**Files to modify:**

- `scripts/setup-consumer.sh` — the `tracker_block` assignment inside `write_skills_config()`, ~L336-338

**Current code** (one `$'...'` string; note the embedded `\n` escapes):

```bash
if [[ "$TRACKER" == "jira" ]]; then
  tracker_block=$'\ntracker: jira\n\njira:\n  # devEstimateField: customfield_10594  # optional …\n  # defaultAssignee: 712020:…  # optional …\n  statusMap:                          # local document status -> your Jira workflow status name\n    draft: To Do\n    planned: To Do\n    ready-for-development: To Do\n    in-progress: In Progress\n    ready-for-review: In Review\n    accepted: Done\n    cancelled: Cancelled'
```

**Replace the `statusMap:` portion with:**

```bash
  tracker_block=$'\ntracker: jira\n\njira:\n  # devEstimateField: customfield_10594  # optional — Jira numeric custom field id for estimated dev hours\n  # defaultAssignee: 712020:00000000-0000-0000-0000-000000000000  # optional — Jira accountId every card is assigned to.\n  #\n  # statusMap — local document status -> your Jira workflow status name(s).\n  # MOST PROJECTS NEED NONE. The built-in candidate lists already cover the\n  # common vocabularies (In Review / Code Review / Waiting for Review / …).\n  # An override REPLACES the candidate list for that status, so adding one\n  # NARROWS matching. Run --probe-workflow first and add only the statuses it\n  # shows being skipped — as ordered lists, not single names:\n  #\n  # statusMap:\n  #   ready-for-review: [Waiting for Review, In Review]'
```

Key points:

- Every generated line under `jira:` is now a comment. Keep two-space indentation on the comment
  markers so the block still reads as belonging to `jira:`.
- Do **not** leave a bare `jira:` key with no children if the other two lines are also commented —
  YAML maps to `null`, which every reader already treats as absent. Verified safe: `parseJiraScalar`
  returns `""`, `loadStatusMap` returns `{}`.

### Phase 3: Detector and test

**Files to modify:**

- `shared/resources/jira-sync.js` — add beside `loadStatusMap` (~L1681)

```js
// The setup wizard used to generate one scalar per status, each equal to the
// FIRST entry of that status's default candidate list. That was correct when a
// map entry was one name; once overrides began REPLACING the list it became a
// silent narrowing. Recognising the fingerprint is the only way an affected
// project finds out — nobody reads a changelog for a file a wizard wrote.
//
// MUST be fed the RAW override block, not loadStatusMap()'s merged output —
// see loadStatusMapOverrides below and the wiring note under it.
//
// eqName is declared later in the file (~L2036). That is fine: this function
// only runs from probeWorkflow, long after module evaluation. Do not "fix" it
// by duplicating the comparison here.
function detectNarrowingStatusMap(statusMap) {
  const map = statusMap || {};
  const keys = Object.keys(map);
  if (!keys.length) return { keys: [], wholeMap: false };
  const hits = keys.filter((k) => {
    const v = map[k];
    if (Array.isArray(v) || typeof v !== "string") return false; // a list is deliberate
    const def = DEFAULT_STATUS_MAP[k.toLowerCase()];
    return !!def && eqName(def[0], v);
  });
  return { keys: hits, wholeMap: hits.length === keys.length };
}
```

**The detector needs the raw override block.** `probeWorkflow`'s local `statusMap` (L2592) is
`loadStatusMap(repoRoot, docKind)` — `{...DEFAULT_STATUS_MAP}` merged with the overrides, ~27 keys
including every alias. Against that, the seven wizard keys are strings and hit, the ~20 alias keys
are still frozen arrays and cannot, so `hits.length === keys.length` is **false for every possible
input** and the detector never fires. Add a raw reader beside `loadStatusMap`:

```js
// The unmerged view of `jira.statusMap`: exactly what the project wrote, with
// no defaults layered in. loadStatusMap() deliberately returns the merged map
// because that is what resolution needs; detection needs the opposite.
// Same swallow-everything discipline — any failure returns {}.
function loadStatusMapOverrides(repoRoot) {
  try {
    const root =
      repoRoot ||
      execSync("git rev-parse --show-toplevel", GIT_EXEC_OPTS).trim();
    const cfgPath = path.join(root, "skills-config.yaml");
    if (!fs.existsSync(cfgPath)) return {};
    return parseStatusMapBlock(fs.readFileSync(cfgPath, "utf-8")).base || {};
  } catch (_) {
    return {};
  }
}
```

Wire into `probeWorkflow`, printed after the candidate-source note (~L2704-2709):

```js
const narrowing = detectNarrowingStatusMap(loadStatusMapOverrides(repoRoot));
if (narrowing.wholeMap) {
  log(
    `\n   ⚠️  Every jira.statusMap entry equals the first default candidate for its status.` +
      `\n      That is the signature of a config generated before v0.35, when an override seeded` +
      `\n      the list rather than replacing it. It is now NARROWING your matching to one name` +
      `\n      per status. Consider deleting the block — see docs/reference/configuration.md.`,
  );
}
```

Export **both** `loadStatusMapOverrides` and `detectNarrowingStatusMap` alongside `loadStatusMap` in
`module.exports` (~L3103).

  (The second parameter is named `issueType` at the definition; callers pass their local `docKind`.)
